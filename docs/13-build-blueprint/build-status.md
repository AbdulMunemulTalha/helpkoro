# Build Status

## Purpose

A single, always-current view of what is actually built in HelpKoro, tracked against the phased [build roadmap](build-roadmap.md). It exists so anyone — engineering, review, or planning — can answer "what is done, what is in progress, and what is left" without reading the whole tree or the git log.

This document has two parts:

- **This narrative** (hand-maintained) — the authoritative account of scope, intentional deferrals, and Validate-gated work that no automated check can infer.
- **The auto-generated block below** — regenerated from repository evidence (which deliverables exist, the live API route surface, ADR/migration/test counts, current git HEAD). It reports what is _present_, which is evidence of progress, not proof of correctness.

When the two disagree, trust the narrative and open an issue — a mismatch usually means a deliverable landed without its documentation, which the [Definition of done](../../CLAUDE.md) forbids.

## How it stays current

The auto block updates itself so no one has to hand-edit checkboxes:

- **On demand:** `pnpm build:status` rewrites the block from the current tree.
- **On every commit (opt-in):** enable the versioned git hooks once per clone and the block refreshes after each commit — every completed part is reflected automatically:

  ```bash
  git config core.hooksPath .githooks
  ```

- **In CI (opt-in):** `pnpm build:status:check` exits non-zero when the committed block no longer matches the tree (it ignores the volatile commit stamp), the same way `format:check` guards formatting.

The generator is [`scripts/build-status.mjs`](../../scripts/build-status.mjs) — zero-dependency Node, idempotent (same tree → identical output).

## What is intentionally not built yet

- **Phase 0 — deferred (provider-gated, Validate):** email/phone verification and password-reset _delivery_. Auth issues no codes until a messaging provider is approved; `email_verified` stays `false`. See [ADR-007](../12-decisions/adr-007-authentication-sessions-and-rbac.md).
- **Phase 1 — Campaigns (backend spine in progress):** the campaign domain model, lifecycle state machine, and review workflow ship per [ADR-008](../12-decisions/adr-008-campaign-domain-model-lifecycle-and-review.md), behind the seeded-disabled `campaigns.creation_enabled` flag and **money-off by design** (no donation/ledger/payout code). Still to come this phase: organizer onboarding/profiles, the public web app (`apps/web`), the operations reviewer UI (`apps/operations`), and the uploads/evidence pipeline (Increments 2–4).
- **Phases 2–4** are not started. Their checklist items below are derived from the [roadmap](build-roadmap.md) and will flip to ✅ automatically as the corresponding modules land; the evidence paths are best-effort and may be renamed when the work is designed.
- **Real-money launch** is blocked until every Bangladesh legal/provider item marked **Validate** has written approval. No real funds move before launch sign-off.
